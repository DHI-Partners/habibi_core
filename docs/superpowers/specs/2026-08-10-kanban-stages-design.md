# Этапы канбан-доски, управляемые из UI (ClickUp-style)

Дата: 2026-08-10
Статус: на согласовании

## Задача

В ERPNext колонка канбан-доски — это не подпись, а значение Select-поля, по которому
построена доска. Из-за этого пользователь не может управлять этапами так, как привык
в ClickUp:

- переименовать колонку нельзя вообще — в API канбана есть только `add_column`,
  `archive_restore_column` и `set_indicator` (`frappe/desk/doctype/kanban_board/kanban_board.py:79-101`);
- кнопка «Добавить колонку» дописывает колонку только в доску, но не в Options поля,
  поэтому перетащить карточку в новую колонку невозможно: `_validate_selects`
  отвергает значение, которого нет в Options (`frappe/model/base_document.py:1119`);
- канбан умеет строиться только по Select-полю (`kanban_view.js:384-386`), поэтому
  справочник-Link (естественное решение «этапы как записи») не подходит.

Нужно: пользователь сам создаёт доски с произвольными наборами этапов и переименовывает
этапы прямо в интерфейсе, без обращения к разработчику.

## Что делаем

Слой в `habibi_core`, который закрывает разрыв между колонками доски и значениями поля.
Механизм универсальный: работает для любой доски по любому пользовательскому Select-полю,
а не для одной конкретной доски.

### Компонент 1. Поле «Этап»

Custom Field в Task, в fixtures (`habibi_core/fixtures/custom_field.json`) — чтобы поле
жило в git и переезжало на другие окружения, а не только руками в проде:

| Свойство | Значение |
|---|---|
| `dt` | Task |
| `fieldname` | `custom_stage` |
| `label` | Этап |
| `fieldtype` | Select |
| `options` | Бэклог / В работе / На проверке / Готово (по строке) |
| `default` | Бэклог |
| `insert_after` | `status` |
| `in_standard_filter` | 1 |

В `hooks.py` в `fixtures` добавляется запись с фильтром по `name in ["Task-custom_stage"]`,
по образцу существующей записи для Translation.

Стандартные `status` и `priority` не трогаем — они продолжают работать как раньше.

Осознанная цена: значения хранятся в БД по-русски, потому что их вводит пользователь.
При переключении интерфейса на английский этапы останутся русскими. Это неизбежно,
если пользователь сам создаёт названия.

### Компонент 2. Синхронизация «колонка → значение поля»

Модуль `habibi_core/kanban_stages.py`, подключённый через
`doc_events["Kanban Board"]["on_update"]`.

При сохранении доски: колонки, которых нет в Options поля, дописываются в конец Options.
Итог для пользователя — «Добавить колонку» на доске работает так же, как создание статуса
в ClickUp: колонка появилась, карточки в неё перетаскиваются.

Правила:

- **Хук срабатывает только если поле доски — Custom Field типа Select.** Стандартные поля
  ERPNext (`status`, `priority`) не затрагиваются ни при каких условиях. Это главная
  защита: ошибка в хуке не должна испортить стандартную схему.
- Значения из Options **не удаляются никогда**, даже при архивировании колонки — иначе
  задачи в архивированной колонке стали бы невалидными и перестали сохраняться.
- Если новых колонок нет — ранний выход. `on_update` у доски дёргается в том числе при
  перетаскивании карточек, лишней работы там быть не должно.

### Компонент 3. Переименование этапа

Whitelisted-метод `rename_stage(board_name, old_name, new_name)` в том же модуле.

Проверки до начала работы:

1. `new_name` непустой после `strip()`;
2. права на запись у доски и у её `reference_doctype`, иначе `frappe.PermissionError`;
3. поле доски — Custom Field типа Select (тот же признак, что и в хуке);
4. `old_name` есть среди колонок, `new_name` — нет.

Порядок изменений (важен: сначала расширяем допустимые значения, потом переносим данные,
и только затем убираем старое):

1. добавить `new_name` в Options поля;
2. перевести документы: `UPDATE tab<DocType> SET <field>=new, modified=now(), modified_by=<user> WHERE <field>=old`;
3. переименовать колонку в `Kanban Board Column`;
4. убрать `old_name` из Options;
5. сбросить кеш доктайпа.

Массовый UPDATE вместо пообъектного сохранения — сознательный выбор: это переименование
справочного значения, а не смысловое изменение задач. Записи в `Version` не создаются,
но `modified` обновляется, чтобы не отдавались устаревшие кеши. Имена таблицы и поля
берутся из метаданных проверенного Custom Field, а не из пользовательского ввода.

### Компонент 4. Пункт меню на доске

`habibi_core/public/js/kanban_stages.js`, подключается через `app_include_js`.

Хука для канбан-вью в Frappe нет, поэтому единственная точка входа — обернуть
`frappe.views.KanbanView.prototype.push_menu_items` и дописать пункт «Переименовать этап»
(показывается только при `board_perms.write`).

Риск: `KanbanView` грузится лениво, на `app_ready` класса может ещё не быть. Поэтому патч
ставится по событию роутера при первом заходе на канбан, с защитой от повторного
применения через флаг на прототипе.

Диалог: Select с текущими колонками + поле нового названия → `frappe.xcall` →
обновление доски.

## Тестирование

`habibi_core/tests/test_kanban_stages.py`:

1. синхронизация дописывает новую колонку в Options;
2. синхронизация игнорирует доску по стандартному полю (`priority`) — Options не меняются;
3. переименование переносит задачи, правит Options и колонку;
4. переименование отклоняет пустое имя и дубликат;
5. переименование отклоняет доску по стандартному полю;
6. переименование отклоняет пользователя без прав на запись.

Где гонять: локального bench нет, а `bench run-tests` создаёт тестовые записи прямо в БД
указанного сайта — **на проде запускать нельзя**. Поэтому в docker-стеке на сервере
поднимается временный сайт (`bench new-site test.habibi.local`), тесты идут на нём,
после прогона сайт удаляется.

## Выкатка

Проверенная схема CI (важно: она отличается от того, как предполагалось):

- образ собирает workflow `habibi-image.yml` в репозитории **habibi_docker**, а не в
  habibi_core; `habibi_core` он тянет из ветки `main` (`habibi/apps.json`);
- выкат на прод — по тегу `v*` **в habibi_docker** (job `deploy`: бэкап всех сайтов →
  правка `CUSTOM_TAG` в `.env` → `docker compose pull && up -d` → миграции);
- в habibi_core нет `.github` вообще — ни workflow, ни `repository_dispatch`, тегов тоже нет.

Значит порядок такой: код в `habibi_core/main` → тег `v1.0.1` в **habibi_docker** →
сборка подтянет свежий main и выкатит. Тег в habibi_core сам по себе не соберёт ничего.

Опционально позже: добавить в habibi_core workflow с `repository_dispatch`
(тип `habibi-apps-updated` уже поддержан в habibi-image.yml), чтобы образ пересобирался
на пуш, без ручного тега.

## Работы на проде после выкатки

- удалить доску `Habibi CRM` (построена по приоритету, отфильтрована по тестовому проекту
  `PROJ-0002` «FSA Test», пользователю не нужна);
- создать доску по полю «Этап»;
- убрать Property Setter `Task-main-default_view = Kanban`, либо оставить осознанно:
  именно из-за него открытие «Задач» сразу уходило в канбан и упиралось в ошибку.

Всё это — только после подтверждения пользователя.

## Что сюда не входит

- Отдельный доктайп-справочник этапов: канбан работает только с Select-полем.
- Разные наборы значений поля для разных досок. Пул значений в поле общий, но **набор
  колонок у каждой доски свой** (`Kanban Board Column` — отдельная таблица под доску),
  поэтому визуально доски независимы, как списки в ClickUp.
- Автоматическое скрытие карточек: если у задачи этап, которого нет в колонках открытой
  доски, карточка на этой доске не показывается. Поведение штатное, менять не будем.
- Исправление апстрим-бага Frappe с указателем на удалённую доску
  (`kanban_view.js:12` не проверяет существование). Отдельная задача.
